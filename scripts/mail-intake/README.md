# 收信資料夾 → 電號主檔 → EasyFlow 待審表

沿用 Outlook 工具下載的 `ready/日期/原始檔名.pdf`，此工具遞迴掃描 PDF，透過平台既有上傳與辨識 API 產生單據，再取得 EasyFlow 待審表。主檔對應與金額計算全部由平台負責，不另寫第二套規則。沒有送出 EF、工作流核准、寄信或刪除來源檔的動作。

## 前置

- 平台更新到本次版本，OCR 服務可用。
- 將已核對的電號大表匯入**同一組織**的案場／電號主檔；方法見 `scripts/data-import/README.md`。
- Node.js 22 以上（可使用 Outlook 收件安裝包內的 Node 執行檔，不需 npm 安裝依賴）。
- 使用可上傳附件、操作收件、讀取電費單的專用帳號；帳密透過執行環境提供，不寫進 Git 或指令參數。

## 執行一輪

```powershell
# 先在執行環境設定 EO_INTAKE_USER 與 EO_INTAKE_PASSWORD。
# 換成實際平台位址及組織 ID，下面的 1 只是本地測試範例。
node .\ingest-folder.mjs --folder 'C:\EnergyOps\WebMailInbox\ready' --state 'C:\EnergyOps\PlatformIntake' --base-url 'http://127.0.0.1:11950' --org-id 1
```

正式遠端部署先手動執行一輪核對，之後由現有排程每 30 分鐘執行同一指令。不要同時啟動兩個工作。遠端排程帳號、環境變數與中斷連線行為尚須在客戶環境驗證；本次不會自動替客戶建立排程。

## 產出與復原

- `last-run.json`：每份檔案的結果、批次／單據 ID、直接開啟平台審核畫面的網址。
- `forms/<內容雜湊>.html`：可閱讀、可列印的申請表快照。原始 PDF 不改名、不搬移。
- `state.json`：內容 SHA256＋目標平台／組織去重。同一內容改檔名或出現在其他日期也不重複匯入。**請備份且不要刪除**；換目標資料庫時使用新狀態目錄。
- `still_downloading`：檔案最後修改不到 30 秒，本輪略過；下輪再掃。
- `recognizing`：辨識尚未完成，下一輪沿用相同批次查詢，不重新上傳。
- `failed / unclassified`：到平台檢查辨識問題；不把未辨識的單標成完成。
- `needs_reconciliation`：建立批次時連線中斷，無法確認是否成功；先核對平台，不自動重送。上傳回應遺失時，工具先讀同一批次核對是否已有附件。
- `scan.lock`：防止同時執行；程序異常結束後，先確認沒有匯入程序在跑，才手動刪除此鎖檔。

已完成的 HTML 是當時快照。之後人工校對或主檔變更，請從平台重新開啟表單及下載最新版本，不能把舊 HTML 當成正式核准單。

平台「儲存申請草稿／確認申請內容」保存承辦欄位、確認人與時間；來源改變時舊確認失效。這是送 EF 前的內容準備，**不取代平台既有簽核或 EF 內部簽核**。公司代碼、部門與正式申請選項沒有來源時仍留待補齊。地主租約不會阻擋開票／電費付款草稿。
